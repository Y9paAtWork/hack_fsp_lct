# Техническая документация FSP Career

## 1. О проекте

FSP Career решает две связанные задачи. Кандидату система подбирает вакансии, а работодателю — кандидатов для конкретной вакансии. В обоих случаях используется одна и та же информация: опыт, технологии, результаты тестов, активность и достижения ФСП.

Проект сделан как обычное клиент-серверное приложение. React отвечает за страницы и формы. FastAPI принимает запросы, проверяет права и выполняет расчёты. SQLite хранит данные. Frontend напрямую с базой не работает.

## 2. Из чего состоит система

| Часть | Реализация | За что отвечает |
|---|---|---|
| Frontend | React 18, Vite | Интерфейс кандидата и работодателя |
| Backend | FastAPI, Uvicorn | API, проверки, бизнес-логика |
| База | SQLite, WAL | Профили, вакансии, тесты, векторы и переписка |
| Ранжирование | NumPy, Jina Embeddings v3 | Сравнение вакансий и опыта |
| Пароли | Argon2id | Хеширование паролей |
| Резервные копии | AES-256-GCM | Шифрование файла базы для хранения и передачи |

Пользователь открывает сайт и выполняет действие. React отправляет запрос в `/api`. FastAPI определяет текущего пользователя по cookie, проверяет его роль и только после этого обращается к SQLite. Ответ возвращается в JSON. Готовую frontend-сборку backend раздаёт из папки `dist`.

## 3. Frontend

Исходный код интерфейса находится в `src`. Основные страницы покрывают регистрацию, профиль, тестирование, поиск вакансий, кабинет работодателя и взаимодействия между сторонами.

PDF кандидата разбирается в браузере через `pdfjs-dist`. Извлекается текстовый слой документа. OCR в проекте нет, поэтому скан без текста автоматически разобрать не получится. Все найденные данные можно исправить перед сохранением.

Frontend не получает правильные ответы тестов и не рассчитывает итоговый рейтинг сам. Это сделано на backend, чтобы пользователь не мог изменить результат через инструменты браузера.

## 4. Backend

Точка входа — `backend/app.py`. При старте приложение:

1. открывает или создаёт SQLite;
2. применяет схему и встроенные миграции;
3. загружает справочник технологий;
4. добавляет технологические и ежедневные вопросы, если их ещё нет;
5. подключает статическую сборку `dist`.

Логика вынесена в отдельные модули:

| Файл | Назначение |
|---|---|
| `backend/db.py` | Подключение к SQLite и миграции |
| `backend/profile.py` | Очистка и сохранение профиля кандидата |
| `backend/ranking.py` | Подбор кандидатов для вакансии |
| `backend/candidate_vacancy_search.py` | Подбор вакансий для кандидата |
| `backend/candidate_access.py` | Обезличивание, квоты и аудит |
| `backend/assessments.py` | Технологические и ежедневные тесты |
| `backend/marketplace.py` | Вакансии, отклики, приглашения и сообщения |
| `backend/resume_pdf.py` | Создание PDF-резюме |
| `backend/encrypted_database.py` | Шифрование и восстановление снимка SQLite |

## 5. База данных

Путь по умолчанию — `data/fsp.sqlite3`. Если база лежит в другом месте, используется переменная `FSP_DB`.

SQLite запускается в WAL-режиме. Внешние ключи включены, время ожидания блокировки установлено в 60 секунд. Функция подключения делает commit при успешном завершении операции и rollback при исключении.

Основные группы данных:

| Данные | Таблицы |
|---|---|
| Аккаунты | `users`, `sessions`, `candidate_profiles`, `employer_profiles` |
| Резюме | `resumes`, `work_items`, `resume_technologies` |
| Вакансии | `vacancies`, `vacancy_technologies`, `vacancy_query_vectors` |
| Векторы | `embedding_chunks`, `embeddings`, `item_vectors`, `embedding_runs` |
| Тесты | `test_questions`, `assessment_attempts`, `assessment_answers`, `technology_level_results` |
| Грейды | `candidate_initial_grades`, `candidate_specialization_grades`, `candidate_verified_grades` |
| Активность и ФСП | `candidate_activity`, `daily_sessions`, `candidate_fsp_achievements` |
| Найм | `hiring_interactions`, `hiring_invitations`, таблицы сообщений |
| Доступ работодателя | `candidate_match_access`, `candidate_access_audit` |

Полное описание колонок и ограничений находится в `backend/schema.sql`.

## 6. Аккаунты и права

В `users.role` есть две роли: `candidate` и `employer`. Для каждого защищённого маршрута FastAPI отдельно проверяет текущего пользователя и нужную роль.

Кандидат работает только со своим профилем, тестами, откликами и приглашениями. Работодатель управляет своим профилем компании и своими вакансиями. Переданный из браузера идентификатор сам по себе не даёт доступа: backend дополнительно проверяет владельца вакансии и участника взаимодействия.

Новые работодатели создаются со статусом `pending`. Подбор кандидатов становится доступен после административного одобрения:

```bash
python3 -m backend.approve_employer company@example.org
```

Возможные статусы компании: `pending`, `approved` и `blocked`.

## 7. Вход и сессии

Пароль хешируется Argon2id с индивидуальной солью. Открытый пароль не сохраняется.

После входа создаётся случайный токен сессии. Сам токен отправляется в HttpOnly-cookie `fsp_session`, а в SQLite записывается только его SHA-256. Сессия действует семь дней. Cookie имеет `SameSite=Strict`; флаг Secure включается переменной `FSP_COOKIE_SECURE=1`.

Для запросов, которые изменяют данные, middleware проверяет заголовок Origin и ограничивает тело двумя мегабайтами. Ответы получают `Cache-Control: no-store` и `X-Content-Type-Options: nosniff`.

Ограничение попыток входа сейчас хранится в памяти процесса: 15 попыток с одного IP за пять минут. Для нескольких экземпляров backend такой лимит нужно перенести в Redis или reverse proxy.

## 8. Профиль кандидата

Кандидат выбирает одну или несколько специализаций. Для каждой специализации указывается грейд Junior, Middle или Senior. Также сохраняются технологии, опыт, проекты, зарплатное ожидание и идентификатор ФСП, если пользователь его указал.

Backend хранит номер `revision`. При сохранении профиль отправляется вместе с текущей ревизией. Это защищает от ситуации, когда две вкладки редактируют один профиль и более старая версия затирает новую.

Из профиля синхронизируется запись `resumes`, а опыт раскладывается на `work_items`. Для кандидата можно сформировать отдельное PDF-резюме по выбранной специализации.

## 9. Вакансии

Работодатель указывает название, специализацию, грейд, зарплату, регион, описание, задачи и обязательные технологии. Backend проверяет диапазон зарплаты и названия технологий по справочнику.

Вакансия бывает публичной или приватной, открытой или закрытой. Подбор кандидатов доступен только для собственной открытой вакансии. Импортированные вакансии без `employer_id` нельзя использовать для просмотра кандидатов.

После создания новой вакансии для неё нужно подготовить embedding. Пока вектора нет, вакансия сохранена, но ранжирование по ней работать не будет.

## 10. Как считается рейтинг

В текущей версии формула одна и для каждой вакансии использует четыре компонента:

```text
score = 0.70 × experience
      + 0.25 × skills
      + 0.025 × activity
      + 0.025 × fsp
```

Значения компонентов находятся в диапазоне от 0 до 1.

### Опыт

Текст вакансии и каждый блок опыта представлены 1024-компонентными векторами Jina Embeddings v3. Система сравнивает вакансию с отдельными работами и проектами кандидата, а затем берёт лучший результат. Это не даёт длинному резюме автоматически получить высокий балл только за объём текста.

### Технологии

Для вакансии берутся обязательные технологии. Для кандидата используется skill-вектор нужного грейда. Подтверждённый тест записывает оценку от 0 до 1. Если технология указана в стеке, но тест не пройден, применяется промежуточное значение, предусмотренное текущей логикой.

### Активность

Компонент строится из посещений и завершённых ежедневных тестов за 30 дней. Backend учитывает только серверные события. Значение активности нельзя передать готовым числом из браузера.

### Достижения ФСП

Таблица `candidate_fsp_achievements` хранит уровень соревнования, этап, место и источник записи. Лучшее достижение даёт основную часть балла, остальные добавляют небольшой бонус.

Сейчас достижения ФСП всегда входят в формулу с весом 2,5%. Переключателя на уровне вакансии ещё нет. Это важно не путать с уже работающей интеграцией: внешний реестр ФСП пока не подключён, а часть данных в демонстрационной базе имеет источник `synthetic_demo`.

### Объяснение результата

В ответе API есть итоговый балл и отдельные компоненты. Работодатель может увидеть, за счёт чего кандидат попал в выдачу: опыта, технологий, активности или ФСП. Также возвращаются грейд, обязательные технологии и признак расхождения зарплаты.

## 11. Векторы и worker

Векторы сохраняются в SQLite как `float32`. Для них записываются модель, ревизия, задача, размерность и хеш исходного текста. Если тот же текст уже обрабатывался той же моделью, готовый embedding можно использовать повторно.

Длинный опыт делится на части. После обработки частей формируется нормализованное среднее для всей работы или проекта.

Готовый сайт и поиск по существующим векторам работают на CPU. Отдельный worker нужен для новых или изменённых профилей и вакансий. Он может работать локально или через Jina API. Массовый расчёт на CPU занимает больше времени, но это не мешает запуску интерфейса.

Запуск локального worker:

```bash
python3 -m pip install -r backend/requirements-embeddings.txt
python3 -m backend.embedding_worker --mode local --batch-size 16 --watch
```

## 12. Тесты кандидата

При старте backend загружает банк технологических и ежедневных вопросов в SQLite. Правильные ответы остаются на сервере. Frontend получает только то, что нужно показать пользователю.

Для закрытых вопросов применяется точное сравнение. Развёрнутые ответы могут проверяться через Jina с отдельной версией калибровки. Попытка, ответы, оценка и версия проверки сохраняются в базе.

Лучший результат по технологии хранится отдельно. Грейд ведётся по каждой специализации, поэтому кандидат может, например, иметь разные уровни в Backend и ML/AI.

Ежедневный тест формируется по московской дате. Его результат участвует в расчёте активности.

## 13. Подбор кандидатов и персональные данные

Общий список кандидатов закрыт. Маршруты `/api/candidates` и поиска по имени возвращают `403`. Работодатель начинает с собственной вакансии и получает не более 20 совпадений.

До согласия кандидата в карточке нет имени, email, полного резюме, `user_id` и `resume_id`. Backend создаёт случайный `match_id`, привязанный к работодателю, вакансии и кандидату. Тот же токен нельзя использовать с другой вакансией или другим аккаунтом.

По умолчанию одна компания может получить не более 50 новых карточек в сутки. Повторно открытая карточка не расходует квоту ещё раз. Значение меняется через `FSP_DAILY_CANDIDATE_LIMIT`.

Поиск, приглашение и открытие резюме записываются в `candidate_access_audit`. IP и User-Agent хранятся в виде хеша с секретной строкой `FSP_AUDIT_PEPPER`.

Полное резюме открывается после принятия приглашения кандидатом. Backend проверяет конкретное взаимодействие перед каждой выдачей.

## 14. Отклики, приглашения и чат

Кандидат может откликнуться на вакансию. Работодатель может отправить приглашение из защищённой подборки по `match_id`. Прямые приглашения по произвольному `candidate_id` отключены.

В предложении сохраняются компания, описание, диапазон зарплаты и способ связи. Кандидат видит эти условия до решения. Чат становится доступен в рамках разрешённого взаимодействия.

## 16. Шифрование базы

`backend/encrypted_database.py` шифрует файл блоками по 4 МиБ с помощью AES-256-GCM. Каждый блок получает отдельный nonce и проверку целостности. При восстановлении можно дополнительно выполнить `PRAGMA integrity_check`.

```bash
export FSP_DATA_KEY="$(python3 -m backend.encrypted_database keygen)"

python3 -m backend.encrypted_database encrypt \
  data/fsp.sqlite3 \
  backups/fsp.sqlite3.fspenc
```

Восстановление:

```bash
python3 -m backend.encrypted_database decrypt \
  backups/fsp.sqlite3.fspenc \
  data/restored.sqlite3 \
  --check-sqlite
```

Это защита резервной копии и файла для передачи. Рабочая SQLite остаётся расшифрованной, поэтому серверу нужны закрытые права на каталог `data` или шифрование диска.

## 17. Запуск на обычном оборудовании

Для демонстрации нужен Python, готовая SQLite и несколько гигабайт свободного места. Backend раздаёт уже собранный frontend. Рейтинг считается через NumPy по данным из базы. Генеративная LLM не запускается.

GPU нужен только как ускорение при массовом пересчёте embeddings. Если все необходимые векторы уже готовы, сайт и поиск работают на обычном ноутбуке.

## 19. Что нужно для внешнего размещения

Локальная конфигурация подходит для демонстрации. Для публичного сервера потребуется HTTPS, собственный домен и reverse proxy. Нужно включить `FSP_COOKIE_SECURE=1`, задать точный `FSP_ALLOWED_ORIGINS` и заменить стандартный `FSP_AUDIT_PEPPER`.

База, архивы с резюме, ключ шифрования и секреты не должны попадать в Git или `dist`. Backend лучше запускать от отдельного непривилегированного пользователя. Резервное копирование стоит проверять не только созданием архива, но и пробным восстановлением.

Если появится несколько процессов backend, SQLite и локальные лимиты станут узким местом. Следующий разумный шаг — PostgreSQL для данных и Redis для общих лимитов и сессий.

## 20. Интеграция с реестром ФСП

Сейчас реальный API реестра не подключён. В проекте уже есть `fsp_id` и таблица достижений, поэтому данные можно добавить без полной переделки профиля и рейтинга.

Интеграцию лучше делать через серверный адаптер. Backend получает согласие кандидата, обращается к реестру, сохраняет подтверждённый результат и время проверки. Frontend и реестр не должны подключаться к SQLite напрямую.

Для вакансии планируется настройка:

```text
consider_fsp_achievements: true | false
```

Если значение `true`, подтверждённые достижения участвуют в рейтинге. Если `false`, вес ФСП становится нулевым, а остальные веса нормализуются. Отсутствие достижения не должно исключать кандидата.

Эта настройка пока не реализована. Для неё нужно добавить колонку в `vacancies`, поле в `VacancyPayload`, переключатель в форме и обработку весов в `rank_vacancy`.

## 21. Текущие ограничения

- нет подтверждения email;
- реестр ФСП пока не подключён.
