# FSP Career — сайт, аккаунты, SQLite и Jina v3

## Что находится в проекте

- React-интерфейс и готовая сборка dist.
- FastAPI backend с регистрацией, входом и сохранением профилей.
- SQLite `data/fsp.sqlite3` после распаковки отдельного архива `../fsp-database.zip`: полный импорт резюме и вакансий. Файл БД не хранится в Git.
- Разделённые работы/проекты, вычисленные Jina-векторы и оставшаяся очередь. Точные числа готовых векторов записаны в data/checkpoint.json. Векторизация всего корпуса ещё НЕ завершена.
- SQL-схема backend/schema.sql, описание каждой таблицы DATABASE.md.
- Четырёхсигнальный прототип подбора, команды запуска и методика проверки: [RANKING.md](RANKING.md).
- Справочник 202 технологий, PDF/TXT-парсер и автодополнение.

## Самый простой запуск на Mac

Нужен Python 3.11 или новее. Распакуйте архив; откройте терминал в папке с README.md:

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r backend/requirements.txt
python3 -m uvicorn backend.app:app --host 127.0.0.1 --port 8000
```

Откройте http://127.0.0.1:8000. Готовая сборка включена: npm для этого запуска не нужен. Терминал оставьте открытым.

На первом запуске создайте свой аккаунт: ранее локально заполненная анкета автоматически не переносится. Пароли исходным резюме не назначены: эти записи используются как датасет, а не как активные аккаунты. Для работы с подборкой создайте отдельный аккаунт работодателя.

## Разработка интерфейса

В первом терминале запускайте backend с автоматическим перезапуском при изменении Python-кода:

```bash
npm run backend
```

Во втором, из той же папки:

```bash
npm ci
npm run dev -- --host 127.0.0.1
```

Откройте http://127.0.0.1:5173. Vite отправляет /api в backend. Используйте один адрес постоянно: cookie для localhost и 127.0.0.1 различаются. При изменении frontend обновите сборку `npm run build`, если работаете через порт 8000.

## Профиль кандидата

После входа кандидат сразу попадает в кабинет. Во вкладке «Редактировать» можно добавить и удалить технологии, изменить работу и проекты. На шаге выбора специализаций кандидат указывает грейд Junior, Middle или Senior отдельно для каждого направления. На странице профиля у каждой специализации есть кнопка «Скачать PDF»: в файл входят её грейд и опыт, а также общий стек и контактные данные. Аккаунт кандидата и анкета записываются в БД одной операцией после последнего шага регистрации. Если закрыть страницу раньше, аккаунт не создаётся, а черновик этой регистрации не сохраняется.

«Создать другой аккаунт» сначала выходит из текущего аккаунта, затем открывает выбор роли. Для нового аккаунта нужна другая почта.

## Векторизация

### Вакансии

Из корня `site` рассчитать и сохранить Jina-векторы всех вакансий:

```bash
python3 -m pip install -r backend/requirements-embeddings.txt
python3 -m backend.index_all_vacancies --dry-run
python3 -m backend.index_all_vacancies --batch-size 8
```

Нужна локальная модель в `../models/jina-embeddings-v3`; для другого расположения укажите `--model-path`. Для другой БД используйте `--db /путь/к/fsp.sqlite3`. Можно сначала проверить первые 100 новых вакансий через `--limit 100`, затем запустить команду без лимита. Каждый пакет сохраняется отдельно в `vacancy_query_vectors`; повторный запуск пропускает готовые векторы и пересчитывает только вакансии с изменившимся текстом. Модель кодирует название и обязанности; если отдельная колонка обязанностей пуста, извлекается раздел задач из описания, а при его отсутствии используется только название. Колонки требований и стека в текст для векторизации не добавляются.

Векторы используются в разделе «Поиск вакансии» кабинета кандидата. Там по умолчанию показана ранжированная выдача; соседняя вкладка открывает обычный каталог. Поиск берёт лучший отдельный блок опыта для каждой вакансии и учитывает технологии, активность и подтверждённые достижения с весами 70 / 25 / 2,5 / 2,5. Для навыков выбирается вектор грейда вакансии. Для технологии в стеке без пройденного теста временно используется 0,5, с проверенным результатом на этом уровне — его балл от 0 до 1. При первом поиске недостающие векторы работ и проектов данного кандидата рассчитываются локальной Jina и сохраняются в БД; последующие поиски используют готовые векторы. Если опыта нет, его вклад равен нулю.

Модель: jinaai/jina-embeddings-v3. Локальные веса закреплены на ab036b023d30b4d1138c4c3bfa9f0c445ab455d6, код архитектуры на bd55a5ec8e6c0fb1d6c26efb4b6a4a74ce8a88d3. Проверена совместимость transformers 4.44.2 / sentence-transformers 3.4.1 / einops. Модель запускает свой код из закреплённой HF-ревизии. Веса в архив не включены; при первом запуске загружаются из Hugging Face.

В отдельном терминале:

```bash
source .venv/bin/activate
python3 -m pip install -r backend/requirements-embeddings.txt
python3 -m backend.embedding_worker --mode local --batch-size 16 --watch
```

Локальный worker получает от модели PyTorch-тензоры и преобразует их в обычные списки до передачи NumPy. Это обходит несовместимость моста PyTorch → NumPy, которая на некоторых версиях macOS/Python проявляется ошибкой `RuntimeError: Numpy is not available`.

На GPU-сервере используется CUDA, на совместимом Mac — MPS, иначе CPU. Полный корпус на CPU вычисляется долго. Для разового прогона без ожидания новых профилей уберите `--watch`. Остановка — Ctrl+C, повторный запуск продолжает по состоянию БД. Для повторения неудачных частей добавьте `--retry`. `--max-batches 10` ограничивает диагностический прогон.

Работы и проекты нового зарегистрированного кандидата получают приоритет перед датасетом. Сохранение профиля сразу создаёт записи и задания; API не ждёт тяжёлую модель. Чтобы новые данные получали векторы автоматически, worker должен работать с `--watch`. Статус виден на странице профиля.

Вариант через Jina API: задайте JINA_API_KEY только на сервере и выполните `python3 -m backend.embedding_worker --mode api --reindex --watch`. В этом режиме текст направляется в Jina; локальный режим обрабатывает его на вашем компьютере. API-ревизия помечается отдельно как jina-api-v3-managed. Используйте один режим для полного индекса: версии провайдера и локальные веса не считаются автоматически одинаковыми.

Хранение: task retrieval.passage, 1024 float32-компоненты, L2-нормализация. Длинные тексты делятся на части до 2200 символов без потери текста. Для каждой работы/проекта после обработки всех частей строится нормализованное среднее. SHA-256 текста позволяет повторно использовать совпадающие вычисления. Векторы не подменяются случайными или словарными признаками. Для пустого опыта векторы не создаются.

Для переключения режима или ревизии используйте `--reindex`: старые векторы остаются отдельными записями с собственными метаданными. Локальная модель по официальной карточке имеет CC-BY-NC-4.0: https://huggingface.co/jinaai/jina-embeddings-v3 .

## Импорт и разбиение CSV

Повторно импортировать исходные файлы можно командой:

```bash
python3 -m backend.import_data --resumes /путь/it_resumes_enriched.csv --vacancies /путь/it_vacancies_enriched.csv
```

Исходные CSV не дублируются в архиве: все их поля сохранены в raw_json каждой строки. Одинаковый файл определяется по SHA-256; повторный импорт не создаёт копии. UUID для строк воспроизводимы по виду файла, его хешу и номеру строки. Отсутствующие даты, компания или контакты не выдумываются.

Основной источник — work_experience_text, структура «должность @ компания [начало — окончание]», разделитель ||. При отсутствии полного текста используем work_experience_descriptions. Отдельные списки titles/companies не связываем по позиции: они часто дедуплицированы и имеют разную длину. Неразобранные фрагменты сохраняем и помечаем needs_review. Личные проекты выделяем по явным заголовкам «Проект:», «Projects:» и подобным в описании/дополнительной информации. Простое упоминание проекта в рабочих обязанностях не превращаем в отдельный личный проект. Поэтому это консервативное эвристическое разбиение, а не гарантированная разметка.

При импорте получено 84 550 записей: 84 134 работы, 369 явно выделенных проектов, 47 неклассифицированных фрагментов. 4 306 записей требуют ручной проверки. У 25 901 резюме work_experience_text пуст. Встречаются записи с частичной информацией в других колонках; они сохраняются по fallback-правилам.

PDF-парсер работает в браузере, читает текстовый слой, восстанавливает строки, очищает символы и применяет эвристики навыков/опыта. OCR отсутствует. Все результаты в анкете редактируемые. Подсказки берутся из technology_stack_FINAL.csv, поддерживают алиасы и выбор клавиатурой.

## Аккаунты и API

Пароли — Argon2id с индивидуальной солью. В БД хранится только SHA-256 случайного токена сессии, в браузере — HttpOnly/SameSite=Strict cookie на 7 дней. После выхода сессия удаляется. Кандидат работает только со своим профилем; работодатель управляет только своими вакансиями и диалогами. Проверяется Origin для операций записи, есть ограничение попыток входа. Сохранение профиля атомарное и использует revision против конфликтов между вкладками.

Основные маршруты: POST /api/auth/register, POST /api/auth/login, POST /api/auth/logout, GET /api/auth/me, GET/PUT /api/profile, POST /api/profile/reset, GET /api/profile/items, GET/PUT /api/employer/profile, GET /api/candidates, GET /api/candidates/{id}, GET /api/vacancies, GET /api/matches/{vacancy_id}, GET /api/database/stats. Для тестирования: GET /api/tests/technologies, POST /api/tests/technologies/start, POST /api/tests/technologies/{attempt_id}/submit, GET/PUT /api/grades/declarations, GET /api/grades/progress, GET /api/grades/current, POST /api/grades/advance, GET/POST /api/tests/daily, GET /api/activity/calendar.

Это локальная версия. Отклики, приглашения и сообщения хранятся в SQLite; чат становится доступным после одобрения отклика работодателем или приглашения кандидатом. Работодатель может отправить предложение без вакансии через вкладку «Приглашения» или привязать его к своей вакансии в подборе. Название компании, описание, зарплата «от–до» в рублях и способ связи сохраняются в самом приглашении и видны кандидату до принятия. Вакансии по умолчанию публичные и открытые; работодатель может сделать свою вакансию приватной либо закрыть и перенести в архив. Подбор кандидатов и вакансий работает для вакансий с актуальным Jina-вектором. У импортированных вакансий нет владельца-работодателя на платформе, поэтому отклик по ним сохраняется, но некому его одобрить до привязки компании. Восстановление пароля и проверка почты пока не реализованы. Для внешнего размещения потребуются HTTPS, FSP_COOKIE_SECURE=1 и корректные FSP_ALLOWED_ORIGINS. БД, ключи ответов и секреты worker нельзя класть в публичную папку сайта.

Маршруты рынка вакансий: GET /api/employer/overview, GET /api/employer/vacancies, PATCH /api/employer/vacancies/{id}, GET /api/public/vacancies, POST /api/candidate/vacancies/search, POST /api/vacancies/{id}/apply, POST /api/vacancies/{id}/invite, POST /api/invitations, GET /api/employer/candidates/search, GET /api/interactions, GET /api/interactions/{id}, POST /api/interactions/{id}/decision и POST /api/interactions/{id}/messages. PDF резюме кандидата: GET /api/profile/resume.pdf?specialization=Backend.

## Технологические и ежедневные тесты

При запуске backend импортирует в SQLite 1 730 технологических вопросов и 106 общих вопросов из серверных файлов `backend/technology_questions.json` и `backend/daily_questions.json`. Браузер получает только условия и варианты: эталоны, объяснения и скрытые проверки остаются на сервере. Для одиночного и множественного выбора используется точная проверка. Развёрнутый ответ сравнивается с эталоном локальной Jina v3 с задачей `text-matching`; калибровка `jina-v3-text-matching-cosine-v1` и версия банка записываются вместе с результатом. Для такой проверки установите зависимости из `backend/requirements-embeddings.txt`; локальные веса ищутся в `../models/jina-embeddings-v3`, либо задайте `FSP_JINA_MODEL_PATH`.

У каждого кандидата три 202-мерных skill-вектора: Junior, Middle и Senior. Ранжирование выбирает вектор грейда вакансии; специализации кандидата имеют собственные грейды и разделы тестов. Тест по технологии засчитывается от 50/100. Балл записывается в вектор пройденного уровня; успешный тест более высокого уровня ставит 1,0 для той же технологии во всех младших векторах. Результат и зачёт общие для всех специализаций. При результате ниже 50 предлагается младший уровень, а пройденный и старшие закрываются на 30 суток; при результате 50–89 закрываются все уровни; от 90 сразу предлагается следующий уровень, а пройденный и младшие закрываются на 30 суток. Повышение грейда по матрице применяется к каждой специализации отдельно. Подтверждённый грейд хранится отдельно по матрице `backend/grade_matrix.json`; правило `grade-rules-2.0-pass50-tech-only-v1` временно не требует практического кейса. Исходный банк технологических вопросов не проходил экспертную проверку; все подтверждения содержат версию источника для последующего пересмотра.

Ежедневный тест выдаёт три вопроса по активной специализации и подтверждённому грейду (иначе по текущему уровню тестов). Два вопроса по возможности выбираются из близких специализации тем, третий — из общего банка того же уровня. Один набор и одна попытка фиксируются на московскую дату; новый день начинается в 00:00 МСК. Календарь и показатель активности читаются из серверных событий.

Автоматическая проверка кода доступна для Python, JavaScript и SQL через отдельный Docker worker. Запустите Docker daemon и выполните из папки сайта:

```bash
export FSP_SANDBOX_SECRET="$(python3 -c 'import secrets; print(secrets.token_urlsafe(32))')"
docker pull python:3.11-alpine
docker pull node:20-alpine
python3 -m backend.sandbox_worker &
python3 -m uvicorn backend.app:app --host 127.0.0.1 --port 8000
```

Оба процесса наследуют один `FSP_SANDBOX_SECRET`. Worker слушает только `127.0.0.1:8766`; контейнер запускается без сети, монтирования файлов приложения и дополнительных привилегий, с лимитами памяти, процессов и времени. При остановленном Docker worker кодовая попытка остаётся незавершённой без оценки. Для остальных языков кодовые задания не выдаются автоматически.

После запуска Docker выполните `python3 -m backend.sandbox_smoke`: команда проверит Python, JavaScript, SQL, тайм-аут и лимит памяти на реальных контейнерах.

## Проверки

```bash
npm test
npm run test:ui
python3 -m unittest discover -s backend/tests -v
npm run build
python3 -m backend.status
```

Автоматические проверки охватывают регистрацию, изоляцию аккаунтов, тесты и пересдачу, ежедневную смену даты, вектор и грейд, ранжирование и интерфейс. Подменённый encoder и Docker subprocess используются только в unit-тестах на временных БД. Живой прогон кодовых заданий требует запущенного Docker daemon. В рабочей SQLite векторизация вакансий завершена; векторизация всех импортированных резюме ещё не завершена. Счётчики в checkpoint.json относятся к моменту копирования БД.
