# Подбор по четырём сигналам

Текущая версия — диагностический прототип. Тесты по технологиям, активность и достижения ФСП у импортированных кандидатов **синтетические** (`source=synthetic_demo`). Это не результаты реальных людей. Векторы блоков опыта в распакованной БД рассчитаны Jina; для двух выбранных вакансий запросы также закодированы локальной Jina.

## Данные и формула

- Каталог: `backend/technology_stack_FINAL.csv`, 202 технологии. Порядок строк задаёт индексы вектора. `candidate_skill_vectors.vector` — массив из 202 `float32` в диапазоне 0–1. Для технологии в стеке значение равно результату её теста / 100; для отсутствующей технологии — 0. Хэш каталога хранится рядом с вектором. Синтетические результаты тестов ограничены 48–52 баллами; подтверждённые баллы не ограничиваются. Источник хранится в `skill_test_results`.
- Опыт: запрос строится из названия вакансии и выделенного фрагмента обязанностей. Вводный текст и раздел требований отсекаются по заголовкам; отдельные колонки стека и навыков в Jina не отправляются. Для каждого кандидата считается косинус с отдельными векторами работ и проектов; итог опыта — **одно максимальное неотрицательное совпадение**. Без готового вектора опыт равен 0, кандидат остаётся в рассмотрении. Специализация вакансии и кандидата должна совпадать.
- Навыки: технологии вакансии извлекаются из `description` эвристиками на основе словаря `technology_stack_FINAL`: точные названия, частые варианты написания, границы слов и разрешение пересечений в пользу длинного совпадения. Если в описании ничего не найдено, используется существующий каталог технологий вакансии. Балл — среднее значений вектора для найденных технологий; отсутствующая у кандидата технология даёт 0.
- Активность: для реальных событий `0.55 × min(дни за 30 дней / 20, 1) + 0.45 × min(ежедневные тесты за 30 дней / 12, 1)`. Демо-оценка сжата в диапазон 0.48–0.52 при сохранении числа дней и тестов. Реальные дни посещения аккаунта записываются сервером в `candidate_activity_days`; завершённый тест засчитывается только через серверную функцию после проверки ответа.
- ФСП: для подтверждённого достижения `коэффициент уровня × коэффициент этапа × коэффициент места`. Уровень: региональный 0.6, национальный 0.8, международный 1.0; этап: отбор 0.4, финал 1.0; место: первое 1.0, второе 0.85, третье 0.7, участие без места 0.35. Несколько достижений: лучший балл плюс 10% остальных, максимум 1. Синтетические достижения в рейтинге дают только нейтральный сигнал 0.48–0.52.
- Итоговые демонстрационные веса: `0.70 × опыт + 0.25 × навыки + 0.025 × активность + 0.025 × ФСП`. Все компоненты в диапазоне 0–1. API возвращает их отдельно вместе с источниками данных.

База хранится в `data/fsp.sqlite3` и исключена из Git. Путь можно изменить через `FSP_DB`. Архив `../fsp-database.zip` содержит `data/fsp.sqlite3`; для распаковки из папки сайта: `unzip -n ../fsp-database.zip -d .`.

## Повторный запуск

Из папки `site`:

```bash
python3 -m backend.ranking_cli populate-demo
../.venv/bin/python -m backend.ranking_cli index-vacancies --model-path ../models/jina-embeddings-v3
python3 -m backend.ranking_cli benchmark
python3 -m backend.ranking_cli compare-weights
```

Первый шаг можно повторять: подтверждённые баллы тестов не перезаписываются. Второй шаг кодирует две вакансии с подробными обязанностями (ML / AI и Cybersecurity). Для своих вакансий передайте `--vacancy-id ID` один или несколько раз. Индексацию вакансии надо повторить после изменения её обязанностей. Путь к модели можно опустить, если она есть в стандартном кэше Hugging Face.

Результаты прогона находятся в `out/four_signal_eval/`: `top20.md`, `metrics.json`, `weight_comparison.json`, `weight_review.md`, `eval_pairs.csv`. Выборка содержит 60 пар: на каждую вакансию 15 кандидатов нужной специализации с готовым вектором опыта, 5 без него и 10 других специализаций. Для независимой разметки используйте **`blind_review.csv`**: пары перемешаны внутри каждой вакансии, идентификаторы заменены случайными кодами, модельные места и скоры отсутствуют, а опыт кандидата приведён целиком по выделенным блокам. Заполните `human_rank_1_best` (1–30 внутри вакансии) и, если возможно, `relevance_0_3` (0 — нерелевантен, 3 — отличное совпадение), после чего верните только этот CSV. Связь кодов с исходными резюме хранится локально в `.blind_review_key.json` и не содержит модельных мест или скоров. Повторный экспорт не перезаписывает файл с разметкой.

Разметка получена: `blind_review_filled.csv` содержит все 60 рангов и оценок 0–3. Для повторной проверки, переноса меток в `eval_pairs.csv` и пересчёта шести вариантов весов:

```bash
python3 -m backend.review_evaluation
python3 -m backend.ranking_cli evaluate
```

Результаты сохраняются в `human_weight_evaluation.json` и `human_weight_evaluation.md`. Команда `evaluate` отдельно показывает NDCG@10, Recall@20 и MRR для действующих весов. `benchmark` сохраняет существующую разметку и не перезаписывает CSV.

До ручной разметки шесть наборов весов сравнивались только по составу топа, среднему скору опыта и навыков и устойчивости к сдвигам демоданных. Итоги слепой оценки:

| Опыт / навыки / активность / ФСП | NDCG@10 | Spearman внутри специализации |
|---|---:|---:|
| 35 / 35 / 15 / 15 | 0.8877 | 0.8661 |
| 50 / 40 / 5 / 5 | 0.8885 | 0.8790 |
| 55 / 35 / 5 / 5 | 0.8885 | 0.8797 |
| 60 / 30 / 5 / 5 | 0.8911 | 0.8744 |
| **70 / 25 / 2.5 / 2.5** | **0.8936** | **0.8842** |
| 80 / 20 / 0 / 0 | 0.8957 | 0.8789 |

У 80 / 20 NDCG@10 выше на 0.0021, у 70 / 25 выше согласие с полным порядком человека и остаётся небольшой вес дополнительных сигналов. Для демо сохраняем 70 / 25 / 2.5 / 2.5. Это 60 пар и только две вакансии, поэтому различие в тысячные не является надёжным доказательством лучшей конфигурации. Жёсткий фильтр специализации исключил девять положительно оценённых кандидатов, включая одного с оценкой 2; это отдельное ограничение, которое настройка весов не устранит.

### Второй раунд оценки

В `out/four_signal_eval/round2/blind_review.csv` подготовлены **240 новых пар**: восемь вакансий по 30 кандидатов, без повторов кандидатов из первого раунда или внутри второго. Вместе с первым раундом это 300 пар по десяти вакансиям. Для каждой новой вакансии выбрано 8 кандидатов из верхней части выдачи, 5 из середины, 2 из нижней части, 5 без вектора опыта, 5 из смежных специализаций с близким опытом и 5 из других специализаций. В слепом файле порядок перемешан, а группа отбора, ID резюме, места и скоры модели скрыты. Ключ соответствия находится только локально в `round2/.blind_review_key.json`.

Разметка получена в `round2/blind_review_2_filled.csv`: все 240 рангов и оценок заполнены. Повторная проверка и расчёт метрик:

```bash
python3 -m backend.review_evaluation --out out/four_signal_eval/round2 --review out/four_signal_eval/round2/blind_review_2_filled.csv
python3 -m backend.combined_review_evaluation
```

Итоговые отчёты: `out/four_signal_eval/combined_human_evaluation.md` и `.json`. На десяти вакансиях действующие веса 70 / 25 / 2.5 / 2.5 дали NDCG@10 **0.8316**, Spearman внутри специализации **0.8815** и совпадение с человеческим топ-10 **7.7 из 10**. Среди проверенных весов это наибольший средний NDCG@10, но превосходство над 60 / 30 / 5 / 5 всего **0.0006**. Парный bootstrap по вакансиям не подтвердил устойчивого преимущества: 95% интервал разницы 60 / 30 минус 70 / 25 составляет **[−0.0149; +0.0124]**. Текущие веса оставляем без изменений.

Фильтр специализации исключил 53 положительно оценённых кандидата, включая 19 с оценкой 2–3. Для вакансии AI Engineer NDCG@10 составил 0.6318, причём максимальный NDCG@10 при текущем фильтре — 0.7611. Это отдельная проблема допуска кандидатов, не решаемая перенастройкой весов. Выборка специально обогащена сложными примерами; абсолютные значения метрик не следует интерпретировать как точность на случайном потоке вакансий.

### Третий раунд: больше кандидатов для одной вакансии

В `out/four_signal_eval/round3/blind_review.csv` подготовлены **100 новых кандидатов для вакансии AI Engineer / AI-разработчик**. Все 100 резюме отсутствуют в предыдущих двух раундах. Внутри выборки 70 кандидатов специализации ML / AI с вектором опыта, 10 той же специализации без вектора, 10 кандидатов смежных специализаций с близким опытом и 10 из других специализаций. Места и скоры модели, ID резюме и группы отбора скрыты; порядок строк перемешан. Это стратифицированная диагностическая выборка, а не случайная выборка продакшена.

Разметка получена в `round3/blind_review_3_filled.csv`: все 100 рангов и оценок заполнены. Не меняйте исходные тексты и `review_id`. Метрики для этой вакансии пересчитываются командами:

```bash
python3 -m backend.review_evaluation --out out/four_signal_eval/round3 --review out/four_signal_eval/round3/blind_review_3_filled.csv
python3 -m backend.extended_single_vacancy_eval
```

На новых 100 кандидатах веса 35 / 35 / 15 / 15 дали наибольший NDCG@10 (**0.8517**), тогда как действующие 70 / 25 / 2.5 / 2.5 дали **0.7774** и наибольший Spearman среди допущенных (**0.8401**). Из 100 кандидатов фильтр допустил 80; исключены 13 положительно оценённых, в том числе 5 с оценкой 2–3. Подробности — в `round3/human_weight_evaluation.md` и `.json`.

Для этой же вакансии во втором раунде были размечены ещё 30 других резюме. Объединённая оценка релевантности по **130 кандидатам** находится в `round3/combined_ai_130_evaluation.md` и `.json`: NDCG@10 у 70 / 25 составляет **0.7142**, у 50 / 40 — **0.7140**, у 35 / 35 — **0.7033**. Если заменить прежние 30 кандидатов этой вакансии на объединённые 130 и оставить остальные девять вакансий без изменений, средний NDCG@10 для 70 / 25 равен **0.8399** — лучший из шести наборов, но преимущество над 60 / 30 всего **0.0006**. Человеческие места из разных раундов в общий Spearman не объединяются: они заданы в разных группах. Различия между весами малы; действующие веса пока не меняем.

Сравнивать абсолютные метрики третьего и второго раундов напрямую нельзя: состав кандидатов и доля допущенных фильтром различаются. Оба раунда стратифицированы и не являются случайной выборкой продакшена.

| Опыт / навыки / активность / ФСП | Средний опыт, ML / AI | Средний опыт, ИБ | Средние навыки, ИБ | Оценка |
|---|---:|---:|---:|---|
| 35 / 35 / 15 / 15 | 0.564 | 0.712 | 0.338 | Опыт слабее влияет на порядок; прямой опыт prompt engineering на 7-м месте. |
| 50 / 40 / 5 / 5 | 0.564 | 0.718 | 0.332 | Стек сильно влияет, улучшение опыта небольшое. |
| 55 / 35 / 5 / 5 | 0.567 | 0.722 | 0.326 | Почти тот же топ, что при 60 / 30 / 5 / 5. |
| 60 / 30 / 5 / 5 | 0.567 | 0.722 | 0.326 | Разумный мягкий вариант; профиль с прямым prompt-опытом на 3-м месте. |
| **70 / 25 / 2.5 / 2.5** | **0.567** | **0.731** | **0.307** | **Выбран для демо:** прямой prompt-опыт на 1-м месте, сохраняется значимый учёт стека. |
| 80 / 20 / 0 / 0 | 0.567 | 0.742 | 0.269 | Опыт выше, но стек ИБ проседает, а активность и ФСП игнорируются целиком. |

В этой паре вакансий ни у одного кандидата из топ-20 нет нулевого опыта, однако все кандидаты той же специализации без вектора опыта участвовали в расчёте со значением 0. Для промпт-инженера рассмотрено 322 кандидата, включая 168 без вектора; для ИБ — 473, включая 106 без вектора. По корпусу вакансий эвристика нашла хотя бы одну технологию в 22 445 из 25 782 описаний (87.06%). Это покрытие, а не измерение точности извлечения.

При работающем FastAPI работодатель может получить топ через `GET /api/matches/{vacancy_id}?limit=20`. Если запросный вектор вакансии ещё не рассчитан, API возвращает 409. Подтверждённый балл конкретной технологии следует записывать только серверным кодом через `record_verified_skill_test`; функция проверяет, что технология есть в каталоге и стеке кандидата, а затем обновляет соответствующую ячейку вектора. При редактировании анкеты вектор пересчитывается автоматически.
